# Requirements Document

## Introduction

A comprehensive upgrade to the existing Anti-UAV Detection System control center. The existing system is already operational: edge devices run YOLO inference and publish to MQTT, a FastAPI aggregation service consolidates state, a React/TypeScript frontend provides Dashboard, Map, Live Feeds, and PTZ tabs, and TLS cert-based auth secures MQTT. This spec covers all improvements and new features to be layered on top of the working system, including a proper login portal with JWT auth and invite-based registration, a full audit trail of user actions, a modern sidebar-based UI redesign with a card component system, edge device health reporting, a rich device detail view, per-class detection labels with color coding, an enriched map panel, a structured logging system, live feed fixes, simplified launcher GUIs, a certificate wizard, a silent backend data bridge to external automation systems, and Android PWA access.

## Glossary

- **Auth_Service**: The authentication module within the Control_Center_Backend that issues and validates JWTs, manages user accounts, invite tokens, and enforces role-based access.
- **JWT**: JSON Web Token — a signed token issued by the Auth_Service upon successful login, used to authenticate all subsequent API and WebSocket requests.
- **Invite_Token**: A short-lived, one-time-use alphanumeric code generated by an Admin and given to a new user out-of-band. Required to self-register an account.
- **Viewer**: A user role with read-only access to the Control_Center; cannot issue PTZ commands, control commands, or model switches.
- **Admin**: A user role with full access to the Control_Center, including PTZ commands, model switching, user management, and invite token generation.
- **Audit_Log**: A server-side record of every user action (command issued, PTZ command, model switch) with the username, action type, target device, and timestamp.
- **User_Store**: A SQLite database file (`auth.db`) managed by the Auth_Service that persists user accounts and invite tokens across restarts.
- **Health_Reporter**: A new module on the Edge_Device that periodically collects system metrics (CPU, memory, inference FPS) and publishes them to `uav/health/{device_id}`.
- **Health_Payload**: A structured JSON message published by the Health_Reporter containing device uptime, CPU percent, memory percent, inference FPS, frames processed, MQTT reconnect count, and camera reconnect count.
- **Log_Entry**: A structured JSON message published by an Edge_Device to `uav/log/{device_id}` for WARNING-level and above log events.
- **DeviceCard**: A UI component in the Overview page that summarizes a single Edge_Device's status, health, detection counts, and provides quick-action buttons.
- **SidebarNav**: The collapsible left navigation sidebar in the redesigned Control_Center UI.
- **Card**: The base UI component with a dark background, rounded corners, and subtle border used throughout the redesigned Control_Center.
- **StatChip**: A colored pill badge UI component used to display per-class detection counts and status indicators.
- **HA_Bridge**: A new Docker service that silently subscribes to UAV MQTT topics and forwards state data to external automation systems via MQTT Discovery. Runs entirely in the background with no user-facing presence in the control center.
- **Cert_Wizard**: A UI panel in the main launcher that generates TLS certificates and displays their status.
- **PWA**: Progressive Web App — the Control_Center frontend configured with a web app manifest and service worker for installable, offline-capable access on Android.
- **TURN_Server**: A relay server used as a fallback for WebRTC NAT traversal when direct peer-to-peer connections cannot be established.
- **Tracking_Overlay**: The canvas element overlaid on each video feed that draws bounding boxes, class labels, and track IDs from the latest Tracking_Payload.
- **Intersection_Observer**: A browser API used to detect when a DOM element becomes visible in the viewport, used to auto-start streams when feed thumbnails scroll into view.
- **class_counts**: A field on DeviceState in the Aggregation_Service that holds a mapping of detection class label to count, derived from the latest Tracking_Payload.

## Requirements

### Requirement 1: Login Portal, Invite-Based Registration, and Audit Trail

**User Story:** As an admin, I want to control who can access the control center by issuing invite tokens to individuals, so that every user has a named account and every action they take is traceable back to them.

#### Acceptance Criteria

1. THE Auth_Service SHALL expose a `POST /auth/login` endpoint that accepts `{username, password}` and returns a signed JWT on successful authentication.
2. THE Auth_Service SHALL hash and verify passwords using bcrypt and SHALL persist all user accounts in a SQLite `User_Store` (`auth.db`) so accounts survive container restarts.
3. WHEN a JWT is issued, THE Auth_Service SHALL set its expiry to the value of `JWT_TTL_HOURS` (default 8 hours).
4. WHERE the "Remember me" option is selected at login, THE Auth_Service SHALL issue a JWT with a 30-day TTL instead of the default TTL.
5. THE Control_Center_Backend SHALL protect all `/api/*` REST endpoints and the `/ws` WebSocket endpoint with JWT middleware that validates the token signature and expiry on every request.
6. WHEN a WebSocket connection is established, THE Control_Center_Backend SHALL accept the JWT as a `?token=` query parameter and reject the connection with code 4001 if the token is invalid or expired.
7. THE Control_Center frontend SHALL display a full-screen LoginPage with username and password fields, a "Sign In" button, and a "Register with invite token" link before granting access to any other page.
8. WHEN a user successfully logs in, THE Control_Center frontend SHALL store the JWT in `localStorage` and attach it as an `Authorization: Bearer` header on every subsequent API request.
9. WHEN any API request returns HTTP 401 or the stored JWT is expired, THE Control_Center frontend SHALL automatically redirect the user to the LoginPage.
10. THE Auth_Service SHALL expose a `POST /auth/invite` endpoint (Admin only) that generates a one-time Invite_Token with a configurable expiry (default 48 hours) and an assigned role (`admin` or `viewer`).
11. THE Auth_Service SHALL expose a `POST /auth/register` endpoint that accepts `{display_name, username, password, invite_token}`, validates the token (exists, not expired, not already used), creates the user account in the User_Store, marks the token as consumed with the registering username and timestamp, and returns a JWT.
12. IF a registration attempt uses an invalid, expired, or already-consumed Invite_Token, THE Auth_Service SHALL return HTTP 400 with a descriptive error message and SHALL NOT create an account.
13. THE Auth_Service SHALL expose `GET /auth/users` (Admin only) returning all user accounts with their username, display name, role, created_at, and last_login timestamps.
14. THE Auth_Service SHALL expose `DELETE /auth/users/{username}` (Admin only) that deactivates a user account, immediately invalidating all their active JWTs.
15. WHILE a user has the `viewer` role, THE Control_Center SHALL disable all PTZ controls, command-issuing buttons, and model switch controls, rendering them as non-interactive with a tooltip explaining the restriction.
16. THE Auth_Service SHALL record an Audit_Log entry for every `POST /api/command/*` and `POST /api/ptz/*` request, containing: `username`, `display_name`, `action`, `device_id`, `payload`, and `timestamp`.
17. THE Auth_Service SHALL expose `GET /audit?limit=100&username=&device_id=` (Admin only) returning filtered Audit_Log entries.
18. THE Control_Center Settings page SHALL include a "Users" card (Admin only) displaying the user list, an "Generate Invite" button, and a deactivate button per user.
19. THE Control_Center Settings page SHALL include an "Audit Log" card (Admin only) displaying the last 100 user actions with filters for username and device.
20. THE system SHALL bootstrap a default Admin account on first startup using `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD` environment variables, only if no users exist in the User_Store.

### Requirement 2: Modern UI Redesign

**User Story:** As an operator, I want a modern, sidebar-based control center UI, so that I can navigate between system views efficiently and the interface feels professional and consistent.

#### Acceptance Criteria

1. THE Control_Center frontend SHALL replace the existing top tab bar with a SidebarNav containing navigation items: Overview, Map, Live Feeds, Devices, PTZ, Settings, and Logs.
2. THE SidebarNav SHALL be collapsible between an expanded state (240px wide, showing icons and labels) and an icon-only state (64px wide), with the preference persisted in `localStorage`.
3. THE Control_Center frontend SHALL display a top bar containing the system name "Anti-UAV Control Center", a connection status indicator dot (green when WebSocket is connected, red when disconnected), a user avatar showing the logged-in user's display name initials, and a logout button.
4. THE Control_Center frontend SHALL implement a Card base component using CSS custom properties for background, border-radius, border, padding, and box shadow.
5. THE Control_Center frontend SHALL implement a StatChip component as a colored pill badge for displaying per-class detection counts and status labels.
6. THE Control_Center frontend SHALL implement a DeviceCard component that displays: status indicator, device ID, uptime badge, active model name, detection count with per-class breakdown as StatChips, last detection timestamp, and "View" and "Stream" quick-action buttons.
7. THE Control_Center frontend SHALL implement an Overview page displaying 4 summary stat cards (Total Devices, Online Now, Active Detections, Alerts Today) and a grid of DeviceCard components for all known devices.
8. THE Control_Center frontend SHALL implement a Settings page with a card-based layout containing sections for MQTT configuration, certificate paths, model profiles, user management, and audit log.
9. THE Control_Center frontend SHALL define all theme colors as CSS custom properties (variables) and SHALL support a dark/light theme toggle with the preference persisted in `localStorage`.
10. THE Control_Center frontend SHALL use no new UI framework — the card system SHALL be implemented with plain React and CSS variables.

### Requirement 3: Edge Device Health Reporting

**User Story:** As an operator, I want to see real-time health metrics for each edge device, so that I can identify performance issues or hardware problems before they affect detection quality.

#### Acceptance Criteria

1. THE Health_Reporter SHALL publish a Health_Payload to the MQTT topic `uav/health/{device_id}` every 30 seconds.
2. THE Health_Payload SHALL contain the fields: `device_id` (string), `uptime_s` (integer ≥ 0), `cpu_percent` (float in [0, 100]), `memory_percent` (float in [0, 100]), `inference_fps` (float ≥ 0), `frames_processed` (integer ≥ 0), `mqtt_reconnects` (integer ≥ 0), `camera_reconnects` (integer ≥ 0), and `timestamp` (ISO 8601 UTC string).
3. THE Health_Reporter SHALL collect CPU and memory metrics using the `psutil` Python library.
4. THE Aggregation_Service SHALL subscribe to the wildcard MQTT topic `uav/health/#` and store the latest Health_Payload per device_id in the DeviceState.
5. THE Aggregation_Service DeviceState SHALL be extended with a `health` field containing the latest Health_Payload for each device.
6. WHEN a Health_Payload is received, THE Aggregation_Service SHALL push the updated DeviceState to all connected WebSocket clients within 200ms.

### Requirement 4: Edge Device Detail View

**User Story:** As an operator, I want to open a full-page detail view for any edge device, so that I can inspect its health, certificate status, connection history, model configuration, and recent detections in one place.

#### Acceptance Criteria

1. WHEN an Operator clicks a DeviceCard's "View" button, THE Control_Center SHALL navigate to a full-page Device Detail view for that device.
2. THE Device Detail view SHALL display a header section containing: device ID, online/offline status, and uptime formatted as `Xh Ym` (e.g., "2h 34m").
3. THE Device Detail view SHALL display a health metrics section containing: CPU usage gauge, memory usage gauge, inference FPS, and total frames processed.
4. THE Device Detail view SHALL display an authorization section containing: certificate CN, certificate expiry date, last authentication event timestamp, and a warning indicator if the certificate expires within 30 days.
5. THE Device Detail view SHALL display a connection timeline section showing the last N MQTT connect and disconnect events with timestamps.
6. THE Device Detail view SHALL display a model info section showing: active model name, camera mode, and all configured model profiles for the device.
7. THE Device Detail view SHALL display a detection history section showing the last 50 detections with: timestamp, class label, confidence score, and bounding box coordinates.
8. WHEN an Edge_Device starts, THE Edge_Device SHALL read its own TLS client certificate, extract the CN and expiry date, and include a `cert_info` field (`{cn, expires_at, issuer}`) in its `uav/status/{device_id}` payload.
9. THE Aggregation_Service SHALL store the `cert_info` field from status payloads in the DeviceState and expose it via the REST API.

### Requirement 5: Detection Class Labels and Color Coding

**User Story:** As an operator, I want bounding boxes and detection counts to be color-coded by class label, so that I can instantly distinguish drones from birds and other detected objects.

#### Acceptance Criteria

1. THE Tracking_Overlay SHALL render bounding boxes with a distinct color per detection class label, using a configurable color map (e.g., `drone: "#ef4444"`, `bird: "#f59e0b"`).
2. THE Tracking_Overlay SHALL display a class legend overlay in the corner of each video feed showing the color-to-class mapping for classes currently visible in the frame.
3. THE DeviceCard SHALL display per-class detection counts as colored StatChips (e.g., "drone ×2  bird ×1") instead of a single generic detection count.
4. THE Control_Center map panel SHALL display per-class detection counts in the device popup alongside the existing alert information.
5. THE model profile configuration SHALL support an optional `class_colors` field mapping class label strings to hex color strings (e.g., `{drone: "#ef4444", bird: "#f59e0b"}`).
6. THE Aggregation_Service DeviceState SHALL include a `class_counts` field containing a mapping of class label to integer count, computed from the `detections` array of the latest Tracking_Payload.
7. WHEN a new Tracking_Payload is received, THE Aggregation_Service SHALL recompute `class_counts` by counting detections grouped by their `label` field.

### Requirement 6: Map — Rich Device Panel

**User Story:** As an operator, I want to click a device marker on the map and see a rich slide-in panel with live feed, health, sensor data, and quick controls, so that I can act on a detection without leaving the map view.

#### Acceptance Criteria

1. WHEN an Operator clicks a device marker on the map, THE Control_Center SHALL display a slide-in panel on the right side of the map without closing or navigating away from the map view.
2. THE map panel SHALL include an X button that dismisses the panel and returns the map to its full-width state.
3. THE map panel header SHALL display: device ID, online/offline status, uptime, latitude/longitude with a copy-to-clipboard button.
4. THE map panel SHALL embed a small WebRTC video feed that auto-starts when the panel opens for online devices.
5. THE map panel SHALL display a detection summary section with: per-class counts as colored StatChips, last detection timestamp, and a confidence bar showing the highest confidence detection.
6. THE map panel SHALL display a health snapshot section with: CPU percent, memory percent, and inference FPS from the latest Health_Payload.
7. THE map panel SHALL display a sensor data section with: a compass rose SVG showing the current bearing and a pitch angle indicator.
8. WHERE a device has PTZ capability enabled, THE map panel SHALL display PTZ mini-controls for zoom in, zoom out, and home.
9. THE map panel SHALL display quick action buttons: Start Stream, Stop Stream, a Switch Model dropdown, and a "View Full Detail" button that navigates to the Device Detail view.
10. WHEN the viewport width is below 768px, THE map panel SHALL expand to full viewport width.

### Requirement 7: Logging System

**User Story:** As an operator, I want to view structured log entries from all edge devices in the control center, so that I can diagnose issues and audit system events without SSH access to individual devices.

#### Acceptance Criteria

1. THE Edge_Device SHALL publish WARNING-level and above log entries to the MQTT topic `uav/log/{device_id}` with QoS 0 and no retain flag.
2. EACH Log_Entry SHALL contain the fields: `timestamp` (ISO 8601 UTC string), `level` (string: `WARNING`, `ERROR`, or `CRITICAL`), `logger` (string), `message` (string), and `device_id` (string).
3. THE Edge_Device SHALL rotate local log files keeping the last 7 days of logs with a maximum total size of 50MB.
4. THE Aggregation_Service SHALL subscribe to `uav/log/#` and keep the last 500 Log_Entries per device_id in memory.
5. THE Aggregation_Service SHALL expose a `GET /logs/{device_id}?limit=100&level=WARNING` REST endpoint that returns filtered log entries.
6. THE Control_Center frontend SHALL implement a Logs page with a filterable log table supporting filters by device, log level, and time range.
7. THE Logs page SHALL color-code table rows by log level (e.g., WARNING in yellow, ERROR in orange, CRITICAL in red).
8. THE Logs page SHALL auto-scroll to the latest log entry and SHALL pause auto-scroll when the user hovers over the table.
9. THE Logs page SHALL provide an "Export to CSV" button that downloads the currently filtered log entries as a CSV file.

### Requirement 8: Live Feed Fixes

**User Story:** As an operator, I want live feeds to start automatically and display correctly scaled overlays, so that I don't have to manually trigger streams and bounding boxes align with the actual video content.

#### Acceptance Criteria

1. WHEN the Live Feeds page is opened, THE Control_Center SHALL automatically send a `start_stream` command for each online device that does not already have an active stream.
2. WHEN a DeviceCard feed thumbnail becomes visible in the viewport (detected via Intersection Observer), THE Control_Center SHALL automatically send a `start_stream` command for that device if it is online and not already streaming.
3. THE Tracking_Overlay SHALL compute bounding box scale factors using `videoRef.current.videoWidth` and `videoRef.current.videoHeight` (the actual decoded frame dimensions) instead of hardcoded values.
4. THE Tracking_Overlay SHALL listen to the `loadedmetadata` event on the video element to update scale factors when the stream dimensions become known.
5. THE Tracking_Overlay SHALL attach a ResizeObserver to the canvas element to update canvas dimensions when the video element's rendered size changes.
6. WHEN a stream is requested but no video data has arrived yet, THE Control_Center SHALL display a "Waiting for stream…" placeholder with a spinner, visually distinct from the "Stream interrupted" error state.
7. WHEN a stream is interrupted after having been active, THE Control_Center SHALL display a "Stream interrupted" warning with a red indicator.
8. THE Control_Center SHALL support a configurable TURN server URL via a `TURN_SERVER_URL` environment variable for WebRTC NAT traversal fallback.

**User Story:** As a system administrator, I want simplified launcher applications for both the main device and edge devices, so that deployment and configuration require minimal technical knowledge.

#### Acceptance Criteria

9. THE edge launcher GUI SHALL provide a "Test MQTT" button that attempts a connection to the configured broker and displays a success or failure result within 3 seconds.

### Requirement 10: Certificate Wizard

**User Story:** As a system administrator, I want a graphical certificate wizard in the main launcher, so that I can generate and distribute TLS certificates without using the command line.

#### Acceptance Criteria

1. THE Cert_Wizard SHALL be accessible as a "Certs" tab within the main launcher GUI.
2. THE Cert_Wizard SHALL provide input fields for: Server IP and Device IDs (comma-separated list).
3. WHEN the "Generate" button is clicked, THE Cert_Wizard SHALL execute `gen_certs.sh` with the configured parameters and stream the script output to a log display within the wizard.
4. THE Cert_Wizard SHALL display a certificate status table listing each generated certificate file with its CN, expiry date, and a valid/expired badge.
5. EACH row in the certificate status table SHALL include a "Copy to Device" button that accepts a device IP address and copies the three required certificate files (`ca.crt`, `{device_id}.crt`, `{device_id}.key`) to the device via SCP.

### Requirement 11: Silent Backend Data Bridge

**User Story:** As a system administrator, I want UAV detection data to be silently forwarded to external automation systems in the background, so that I can build automations and receive push notifications without any mention of third-party systems in the control center UI.

#### Acceptance Criteria

1. THE HA_Bridge SHALL run as a new Docker service in the Docker Compose stack and SHALL connect to the Mosquitto broker on the internal Docker network (port 1883, no TLS).
2. THE HA_Bridge SHALL subscribe to the MQTT topics `uav/tracking/#`, `uav/status/#`, `uav/health/#`, and `uav/sensor/#`.
3. WHEN the first message is received from a new device_id, THE HA_Bridge SHALL publish MQTT Discovery configuration messages to `homeassistant/sensor/{device_id}/{entity}/config` so that any connected automation system automatically creates the device and its entities.
4. THE HA_Bridge SHALL create the following entities per edge device: UAV Detected (binary_sensor), Detection Count (sensor), Active Model (sensor), Device Status (sensor), Compass Bearing (sensor), CPU Percent (sensor), Inference FPS (sensor), Last Detection timestamp (sensor), and one sensor per detected class label.
5. WHEN a tracking, status, health, or sensor message is received, THE HA_Bridge SHALL publish the corresponding state update to the appropriate state topic.
6. EACH MQTT Discovery config message published by THE HA_Bridge SHALL contain a valid `unique_id`, `name`, `state_topic`, and `device` block.
7. THE HA_Bridge SHALL use a dedicated MQTT client certificate (`ha-client`) generated by the Cert_Wizard for authenticating to the Mosquitto broker.
8. THE HA_Bridge SHALL be implemented in plain Python with no additional frameworks beyond `paho-mqtt`.
9. THE HA_Bridge SHALL have NO user-facing presence in the Control_Center UI — no mention of "Home Assistant", "HA", or any third-party system name SHALL appear anywhere in the frontend.

### Requirement 12: Android Access via PWA

**User Story:** As an operator, I want to install the Anti-UAV Control Center as an app on my Android device, so that I can monitor UAV detections from my phone with a native app experience.

#### Acceptance Criteria

1. THE Control_Center frontend SHALL include a `manifest.json` in `frontend/public/` with the app name "Anti-UAV Control Center", icons, `display: standalone`, and `theme_color` matching the dark theme background.
2. THE Control_Center frontend SHALL include a service worker (`frontend/src/sw.ts`) that caches the app shell for offline access using native browser Service Worker APIs (no Workbox).
3. THE system documentation SHALL include a guide (`docker/wireguard/android-peer.md`) for setting up a WireGuard Android peer with QR code import instructions, enabling secure remote access to the control center.
4. THE system documentation SHALL include instructions for installing the Control_Center PWA on Android Chrome via "Add to Home Screen".

## Correctness Properties

### Property 1: JWT Token Issuance and Verification Round-Trip

*For any* valid username/password pair accepted by the Auth_Service, the JWT issued by `POST /auth/login` must be verifiable by the JWT middleware and must be rejected after the configured TTL has elapsed.

**Validates: Requirements 1.1, 1.3, 1.5**

---

### Property 6: Invite Token Single-Use Guarantee

*For any* Invite_Token that has been successfully consumed by a `POST /auth/register` call, any subsequent `POST /auth/register` call using the same token must be rejected with HTTP 400 and must not create a new account.

**Validates: Requirements 1.11, 1.12**

---

### Property 2: Health Payload Field Ranges

*For any* Health_Payload published by the Health_Reporter, `cpu_percent` must be in [0, 100], `memory_percent` must be in [0, 100], `uptime_s` must be ≥ 0, and `inference_fps` must be ≥ 0.

**Validates: Requirements 3.1, 3.2**

---

### Property 3: Class Counts Sum Equals Total Detection Count

*For any* Tracking_Payload received by the Aggregation_Service, the sum of all values in the `class_counts` mapping must equal the total number of detections in the `detections` array.

**Validates: Requirements 5.6, 5.7**

---

### Property 4: Log Entry Required Fields

*For any* Log_Entry published to `uav/log/{device_id}`, the entry must contain all five required fields: `timestamp`, `level`, `logger`, `message`, and `device_id`, and `level` must be one of `WARNING`, `ERROR`, or `CRITICAL`.

**Validates: Requirements 7.1, 7.2**

---

### Property 5: Backend Bridge Discovery Config Contains Required Fields

*For any* MQTT Discovery config message published by the HA_Bridge for any device, the message must contain a non-empty `unique_id`, a non-empty `name`, a non-empty `state_topic`, and a `device` block with at least an `identifiers` field.

**Validates: Requirements 11.3, 11.6**
